# Automata

A workflow automation tool. You connect a trigger to a chain of steps, Automata runs them when the trigger fires, and you can see exactly what happened on every run.

Think n8n or Zapier: "when a form is submitted, look up the customer, and post a message to Slack" — without writing a service to do it.

## Status

Pre-alpha. Nothing is built yet. This document is the spec being built toward.

## Core concepts

**Workflow** — a directed graph of nodes. One trigger node, then any number of action nodes. Saved as JSON, so it can be version-controlled, diffed, and imported.

**Node** — one unit of work. Takes input, produces output. Three kinds:

- *Trigger* — starts a run. A webhook, a schedule, or a manual click.
- *Action* — does something. Calls an HTTP API, writes to a database, sends a message.
- *Control* — changes the path. Branch on a condition, loop over a list, wait.

**Connection** — an edge between two nodes. The upstream node's output becomes the downstream node's input.

**Run** — one execution of a workflow. Records the input, output, and status of every node that executed, so a failure can be inspected instead of guessed at.

**Credential** — an API key, token, or OAuth grant, stored encrypted and referenced by a node rather than pasted into it.

## How a workflow executes

1. A trigger fires and creates a run with an initial payload.
2. Nodes execute in topological order. A node runs once all of its inputs are ready.
3. Each node's output is stored on the run, keyed by node ID.
4. A node reads upstream data by expression — `{{ $node.fetch_user.email }}` — resolved at execution time.
5. If a node throws, the run stops and is marked failed, unless that node is configured to continue on error.
6. The run ends when no nodes remain. Every node's input and output stays queryable.

Runs are durable: state is persisted after each node, so a crashed worker resumes rather than restarting.

## Design principles

**Inspectable over magic.** Every run shows the real data at every step. A user debugging a broken workflow should never have to guess what a node received.

**Workflows are data.** A workflow is a JSON document with no embedded runtime state. It can live in git, be generated by a script, or be edited by hand.

**The node interface is the product.** Integrations are the bulk of the value, and they will mostly be written by people who are not us. A node is a schema plus a function, and writing one should take an afternoon.

**Self-hostable by default.** It runs from a single container against a Postgres database. No managed services required.

## Architecture

| Piece | Role |
| --- | --- |
| **Engine** | Resolves the graph, executes nodes, persists run state. |
| **API** | REST + webhooks. CRUD on workflows, triggers runs, serves run history. |
| **Worker** | Pulls queued runs and executes them. Scales horizontally. |
| **Editor** | Browser canvas for building workflows and reading run output. |
| **Node SDK** | The contract a node implements, published so integrations can live outside this repo. |

Stack: TypeScript end to end, Postgres for workflows and run history, a queue for run dispatch.

## Roadmap

**Milestone 1 — it runs.** Define a workflow in JSON, execute it via CLI, see node output. Manual trigger, HTTP node, and a transform node. No UI, no database.

**Milestone 2 — it persists.** Postgres, the API, webhook and schedule triggers, run history.

**Milestone 3 — it's usable.** The editor canvas, credential storage, branching and looping.

**Milestone 4 — it's extensible.** The published node SDK, plus enough first-party nodes to be useful out of the box.
